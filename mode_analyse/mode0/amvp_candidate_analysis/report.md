# 扩展 AMVP 候选池可行性分析

## 1. 实验目标

本次统计用于预研以下方案：

> 将 AMVP 候选池从当前 2 个候选扩展到最多 4 个或 8 个，对候选进行启发式或神经网络排序，只选择排名最优的两个 MVP 作为运动搜索起点，并将它们放入最终 AMVP 列表第 0、1 位，后续运动搜索和 AMVP 编码流程保持不变。

分析联合使用 `[AMVP-MVD]`、`[AMVP-CAND-SET]` 和 `[AMVP-CAND]`，将当前标准 MVP、未被标准流程检查的空域候选、TMVP 和 HMVP 候选关联到最终编码 MV。

- 实际传输 MVD 并纳入分析：2,932,537 组

- 候选快照缺失：0 组

- MVD 与候选集合键错配：0 组

新日志能够完整关联最终 MV、当前标准 MVP 和扩展候选。

## 3. 候选池供给能力

候选经过当前 IMV 精度对齐和 MV 去重后：

- 平均原始候选：7.169528 个
- 平均唯一原始候选：4.971044 个
- 保留 STD0、STD1 并追加额外唯一候选后，平均扩展池：5.048251 个
- 至少具有 4 个唯一候选的块：70.050540%
- 至少具有 8 个唯一候选的块：16.227008%

因此建议实现“最多 8 个候选”的可变长度候选池，而不是强制每个块补满 8 个。候选池大小的完整分布见 `pool_size_histogram.csv`。

## 4. 统计基线和 oracle 口径

报告使用两个基线：

1. **实际选择基线**：当前编码器实际选择的 MVP；
2. **当前 2 候选 oracle 基线**：在 STD0、STD1 中分别选择 MVD L1 最小或 MVD bins 最少者。

判断扩展候选本身是否有效时采用第二个、更严格的基线。只有额外候选优于当前两个候选中的 oracle 最优值，才记作扩展候选改进。

扩展池按以下规则构造：

1. 先放 STD0、STD1，相同 MV 去重；
2. 按日志顺序追加不重复的额外空域候选；
3. 追加 TMVP C0、C1；
4. 追加 HMVP 历史候选；
5. `oracle4`、`oracle8` 分别在前 4、前 8 个可用候选中独立计算最小 L1 和最少 MVD bins；
6. `oracle full` 使用全部唯一候选。

分析固定原编码器的最终 MV，并计算：

```text
MVD = final MV - candidate MVP
```

所以这些数据是候选生成能力的 oracle 上界，不是重新搜索和重新编码的实测结果。

## 6. 4 候选方案

相对当前 2 候选 oracle，最多 4 候选可以达到：

- 17.760867% 的块得到更小 L1；
- 15.016793% 的块得到更少 MVD bins；
- 平均 L1 减少 0.408762 pel；
- 平均 MVD bins 减少 0.436566；
- 零 MVD 比例从 18.261526% 增至 22.258099%。

与 8 候选相比，4 候选获得约 74.9% 的 L1 潜在节省、约 68.5% 的 MVD-bin 潜在节省。因此，4 候选适合作为低复杂度版本或第一阶段实现。

## 7. 8 候选方案

相对当前 2 候选 oracle，最多 8 候选可以达到：

- 24.094462% 的块得到更小 L1；
- 21.062957% 的块得到更少 MVD bins；
- 平均 L1 减少 0.545468 pel；
- 平均 MVD bins 减少 0.637594；
- 零 MVD 比例从 18.261526% 增至 24.446921%。

8 候选已经获得完整候选池约 99.1% 的 L1 潜在节省和约 98.2% 的 MVD-bin 潜在节省。继续增加候选数量的边际收益很小，因此**最多 8 候选是更合适的完整预研上限**。

MVD-bin 代理从 6.892101 降到 6.254507，相对下降约 9.25%。这只针对 MVD 二值化 bins，不代表整个码流下降 9.25%，也不是 BD-rate。

## 11. 可行性判断

### 候选生成层面

**可行，而且存在明显的进一步实验价值。**

- 86.36% 的块存在不同于当前两个标准 MVP 的额外唯一候选；
- 24.43% 的块存在严格优于当前两个候选 oracle 的额外候选；
- 21.39% 的块存在 MVD bins 更少的额外候选；
- 8 候选已经接近完整候选池上界；
- HMVP 是最重要的额外候选来源。

### 排序或神经网络层面

当前数据只能证明候选池中存在更好的 MVP，不能证明某个排序器已经能找到它们。oracle 使用最终 MV 生成标签，最终 MV 在真实决策前不可知，不能作为模型输入。

排序器需要回答：

> 能否在不知道最终 MV 的情况下，把有价值的候选稳定地排进前两名？

首要评价指标应为：

- top-2 recall；
- top-2 regret；
- 相对当前 MVP 的 MVD-bin 变化；
- 实际 BD-rate；
- 编码时间和内存开销。

不能只评价 top-1 分类准确率。

## 12. 推荐实现路径

1. 构造最多 8 个、完成 IMV 对齐和 MV 去重的候选；
2. 保证包含当前 STD0、STD1，防止排序退化时丢失基线；
3. 加入额外空域 A1、B1、B2；
4. 加入 TMVP C0、C1；
5. 加入多个 HMVP，HMVP 应作为重点；
6. 为候选计算不依赖最终 MV 的编码端可用特征；
7. 使用启发式或轻量网络打分；
8. 只保留分数最优的两个候选作为 ME 起点；
9. 将其写入最终 AMVP 列表第 0、1 位；
10. 后续搜索、MVD 编码和语法流程保持不变；
11. 排序置信度低时回退到 STD0、STD1。

建议先实现确定性的轻量排序基线，再训练 NN，以区分候选池扩展和网络排序各自的收益。

## 13. 机器学习数据建议

统计脚本可以导出逐候选数据：

```bash
python3 \
  /ssddata1/V_code/nextcodec-Next/nextcodec-Next-1.0_amvp/tools/analyze_amvp_candidates.py \
  /ssddata1/V_code/test_results/HHI_500_NNdimd_AMVP_print \
  -o /ssddata1/V_code/test_results/HHI_500_NNdimd_AMVP_print/amvp_candidate_analysis \
  --export-training /ssddata1/V_code/test_results/HHI_500_NNdimd_AMVP_print/amvp_candidate_analysis/training_candidates.csv.gz
```

推荐标签：

- 主标签：`target_bins_proxy`
- 辅助标签：`target_l1_pel`
- 排名标签：`target_is_best_bins`、`target_is_best_l1`

`target_*` 由最终 MV 产生，只能作为训练标签，不能作为编码器输入。训练、验证和测试必须按序列或视频内容隔离，不能随机拆分同一序列的相邻 CU，否则会产生数据泄漏并高估 top-2 recall。

## 14. 重要限制

1. oracle 固定原编码器最终 MV，没有从每个额外 MVP 真正重新运行 ME；
2. 新搜索起点可能改变最终 MV、失真和完整 RD cost；
3. MVD syntax-bin proxy 是二值化 bin 数，不是实际 CABAC bit；
4. MVD-bin 下降不能直接解释为整个码流比例或 BD-rate；
5. 最终结论必须通过实际实现、重新编码、BD-rate 和编码时间验证；
6. NN 的特征准备和推理开销可能抵消部分收益。

## 15. 最终结论

- **4 候选方案**适合作为低复杂度基线，可以获得大部分候选扩展收益；
- **8 候选方案**更适合作为完整预研方案，已覆盖约 98%～99% 的全候选池 oracle 潜力；
- **HMVP 历史候选**是最主要的改进来源，应优先保留和建模；
- 最终只保留两个 MVP 搜索起点可以维持现有 AMVP 编码流程，但排序器必须具有较高的 top-2 recall；
- 当前结果是候选覆盖能力的 oracle 上界，下一步需要实现实际排序和双起点 ME，并用 BD-rate 与编码时间验证。

总体判断：**该方案具备明确的预研可行性。推荐以“最多 8 候选池 + top-2 排序 + STD 候选保护/回退”为主方案，以“最多 4 候选池 + 轻量启发式排序”为低复杂度对照方案。**
